# 实体回收机制

假定用于获取下一个可用实体的函数是

```c
extern Entity current_entity;
Entity next_entity(void);
```

内部实现是

```c
return current_entity++;
```

优点是实现简单。缺点是实体回收后不再被利用。如果游戏内实体频繁增删，将会导致后面的实体序号越来越大。

在[稀疏集](稀疏集.md)提到Sparse Set以实体作为下标。无限增长的entity id将会导致数组越界。

那么求余(%)方式可行吗？

```c
return (current_entity + 1) % ENTITY_NUM_MAX;
```

这样解决了数组越界的问题，但是这段逻辑并没有判断下一个实体id是否被占用的能力，使用它会有覆盖已存在实体的风险。而且频繁增加实体的情形下求余运算显得过重。

我们可以考虑新设一个**空闲栈**，栈底在大端。

```c
static Entity __ea_pool[ENTITY_MAX_NUM]; // 使用池
static size_t next_avail = 1; // 栈指针
```

空闲栈初始化为递增实体id：

```c
for (int id = 1; id <= ENTITY_MAX_NUM; id++) { // 0号作为无效位
	__ea_pool[id] = id;
}
```

获取下一个空闲实体id的实现：

```c
Entity next_entity(void) {
	if (next_avail == ENTITY_MAX_NUM) return 0; // 返回0代表分配失败
	return __ea_pool[next_avail++]; // 弹出一个可用id
}
```

新实体编号的问题解决了，接下来是解决旧实体的回收问题。

一个待回收的实体可能已经有**关联一些组件**。这些组件的存在依赖实体。当调用实体销毁函数时，应该先将挂载的组件移除，然后移除实体本身。

```c
void despawn_entity(Entity e, void** dense_sets, int** dense_lens, int** sparse_sets, size_t* comp_sizes, size_t comp_num);
```

这个函数签名太长了，所以最好将形参先封装一下。考虑到每次调用用户都需要手动拿到该实体的所有组件并传递，太复杂。所以可以考虑一张**组件注册表**。假设这张表提前注册好了游戏自己的组件信息。

```c
typedef struct {
	void* dense_set;
	int* dense_len;
	int* sparse_set;
	size_t comp_size;
} CompType;
typedef struct {
	CompType* comps;
	size_t comp_num;
} CompTypeReg;
```

其中`CompTypeReg`内部数组可以是静态的也可以是动态的，具体取决于实现。由于这是游戏引擎端，无法假定其上游戏所用的组件种数，故不应提前限制数量，而是更推荐动态数组的形式。

> 推荐使用C语言数据结构单头库**stb_ds.h**实现动态数组存储。此时`size_t comp_num`不再需要。

以下实现示例，基于**stb_ds.h**：

```c
void despawn_entity(Entity e, CompTypeReg* reg) {
	for (int i = 0; i < arrlen(reg->comps); i++) { // 删除实体挂载的所有组件
		CompType* cur_type = &(reg->comps[i]);
		ecs_del(cur_type->dense_set, cur_type->dense_len, cur_type->sparse_set, cur_type->comp_size, e, NULL);
	}
	if (next_avail > 0) {
		__ea_pool[--next_avail] = e; // 回收实体
	}
}
```

> 可以考虑添加操作成功与否的反馈逻辑，返回值或者参数回传等形式。这里简化表达。
